# Проектные операции Социотеха

Работай как оператор структурированной модели проекта. Не подменяй владельца
проекта, администратора пространства и экспертов по нотациям.

## Обязательный справочник

Перед любой работой через MCP прочитай
[`references/sociotech-mcp.md`](references/sociotech-mcp.md).

Для периодического обзора внешних факторов, проверки прогнозов и сигналов
о пересмотре стратегии прочитать
[`references/strategy-review-cycle.md`](references/strategy-review-cycle.md).

Для содержательной работы дополнительно используй профильный скилл:

- `linked-swot` — факторы, ставки и их связи;
- `hypothesis-mapping` — цели, метрики, субъекты, гипотезы и задачи;
- `story-implementation-map` — рабочие истории, формы реализации и UI-блоки.

## Сначала обнаружить возможности

1. Получить актуальный список MCP-инструментов и их входные схемы в текущем
   клиенте.
2. Сопоставить с запросом чтение, поиск, изменение, аудит, историю, экспорт,
   описания, ответственных и ИИ-контекст.
3. Использовать только реально доступные операции и поля.
4. Если публично заявленная функция отсутствует, не придумывать имя
   инструмента и не подменять её более узкой операцией. Сообщить о расхождении
   и предложить обновить или переподключить MCP в клиенте.

Набор MCP развивается, а клиент может кэшировать старые схемы. Не считать
однажды увиденный список постоянным.

## Безопасно определить контекст

Перед изменениями:

1. Определить пространство и проект без угадывания.
2. Проверить режим доступа, включая признаки публичного проекта, только для
   чтения и разрешения на изменение, экспорт и ИИ-операции.
3. Прочитать обзор проекта, карты и затрагиваемые сущности.
4. Прочитать доступный содержательный контекст: описания проекта и карт, цели,
   соседние и связанные элементы, заметки, блокеры, вложения, источники и
   связанные карты других типов.
5. Составить краткую рамку контекста: границы задачи, принятые определения,
   подтверждённые факты, решения, источники, предположения и неизвестное.
6. Получить ревизию проекта и версии изменяемых полей, если они доступны.
7. Для массовой операции показать пользователю границы, типы изменений и
   ожидаемые удаления. Не запрашивать повторное подтверждение, если точный
   пакет уже явно поручен.

Считать контекст проекта основанием для интерпретации, а не декоративным фоном.
Не объявлять изолированную карточку неполной, если её термин однозначно задан
целью, картой или связями. Одновременно не использовать контекст для оправдания
ошибки нотации. При конфликте источников показать расхождение и не выбирать
версию молча.

Для точечной операции читать минимально достаточный контур: обзор проекта,
метаданные карты, затрагиваемый элемент, его соседей и основания. Не загружать
весь большой проект без необходимости. Если часть контекста недоступна через
MCP, обозначить границу и считать содержательную оценку предварительной.

Публичный проект считать только для чтения, пока runtime явно не подтвердил
обратное. Не просить токены, пароли или коды авторизации в чате.

## Найти проект

Искать на требуемой пользователем широте:

- текущее пространство;
- все доступные пространства;
- публичные проекты;
- аккаунты участников.

Не выдавать поиск только в текущем пространстве за глобальный. При нескольких
равно подходящих результатах показать различающие признаки и запросить выбор.
Переключение текущего пространства выполнять осознанно и проверять после него
контекст следующих вызовов.

Различать поиск названия в текущем пространстве и полнотекстовый поиск
доступных проектов. Членство в пространстве само по себе не открывает каждый
закрытый проект. Найденный аккаунт не считать участником команды проекта.

## Изменять описания и ответственных

Использовать отдельные операции из справочника. Перед изменением прочитать
описание карточки и текущие `responsibleUserIds`. Для назначения выбирать
человека среди участников именно этого проекта; глобальный поиск аккаунта
не подтверждает право назначения. Не менять состав команды, роли и других
ответственных как побочный эффект. Пустая строка описания означает очистку.

## Прочитать и проанализировать проект

Для обзора всего проекта:

1. Прочитать обзор и список карт.
2. Получить Связанный SWOT, все Карты гипотез и КРИ.
3. Выполнить комбинированный структурный аудит, если операция доступна.
4. Проверить сквозную трассировку профильными скиллами. Для перехода из
   Связанного SWOT убедиться, что каждая использованная ставка связана с
   конкретной гипотезой штатной межкартовой связью, а не только маркером или
   текстовой ссылкой.
5. Отделить данные сервиса от содержательных выводов и предположений.

Перед выводами проверить, меняют ли описания, заметки, материалы или другая
карта смысл кратких формулировок. Не требовать повторять в каждой карточке
контекст, который однозначно наследуется из структуры проекта.

Структурный аудит не заменяет методическую проверку нотации.

## Замыкать анализ на проверку стратегии

По процессу регулярного обзора сопоставлять новые внешние факты и результаты
с предыдущим успешным обзором. Проходить реальные связи фактора, ставки,
гипотезы, субъекта или прямого механизма, цели и метрик. Разделять прогноз,
ожидаемый эффект и датированное наблюдение; не переписывать прежний прогноз.

Возвращать сигналы с источником, затронутыми ID, изменившейся предпосылкой
и предлагаемым решением. По умолчанию мониторинг не меняет проект. После
согласованного обновления перечитать результат и сохранить основание
решения для следующей проверки. Ежемесячный ритм — возможная отправная точка,
но реальное расписание настраивать только по поручению через доступный
планировщик. Описание процесса не выдавать за работающую автоматизацию.

## Работать с историей и версиями

Для вопроса «что изменилось» читать историю проекта с пагинацией за весь
нужный период. Группировать события по сущностям и смыслу, различать создание,
изменение, перемещение, связь и удаление.

История — журнал, а не автоматический откат. Не обещать Undo/Redo через MCP,
если соответствующей операции нет. Для отдельной сущности сопоставлять её
историю с текущими связями; явно помечать реконструкцию как вывод, если старое
состояние не возвращено сервисом.

Перед зависимой серией запомнить ревизию. Если она изменилась из-за параллельной
работы, перечитать затронутый контур и пересчитать план, а не перезаписывать
чужие изменения.

## Выполнять ИИ-операции

1. Проверить разрешение на ИИ-операции и доступность нужного запуска.
2. Если задача опирается на файл или текст, загрузить его в ИИ-контекст проекта,
   дождаться обработки источника и проверить извлечённые факты по справочнику.
   Затем запустить генерацию или валидацию один раз.
3. Дождаться терминального состояния штатной операцией ожидания или опроса.
4. Получить список предложенных изменений.
5. Показать пользователю содержательный эффект, а не только идентификаторы.
6. Принять и отклонить только согласованные рекомендации.
7. Перечитать проект и выполнить профильную проверку нотации.

Не считать успешный запуск успешным применением. Не принимать все рекомендации
автоматически и не повторять запуск после тайм-аута без проверки состояния.

## Выполнять массовые изменения

Для импорта, миграции или рефакторинга:

1. Разобрать исходные материалы доступными клиенту средствами.
2. Построить соответствие исходных элементов типам и связям Социотеха.
3. Отделить существующие сущности, обновления и новые кандидаты.
4. Выполнять пакет по зависимостям и небольшими проверяемыми сериями.
5. После каждой серии перечитывать изменённый контур.
6. В конце сравнить ревизию, полный граф и историю фактических операций.

При миграции `стратегическая ставка → гипотеза` создавать элементы и отдельную
структурную связь разными операциями. В текущей схеме операция связи принимает
`boardId`, `hypothesisId` и `strategicBetId`; при нескольких парах использовать
пакетную форму. Не заменять связь заметкой или маркером использования.

Наличие файла у пользователя не означает наличие специальной MCP-операции
импорта. Если её нет, не называть последовательность обычных операций
«встроенным импортом».

## Экспортировать результат

Проверить разрешение на экспорт и выбрать точный тип карты. Вернуть фактически
полученный файл. Не утверждать, что экспорт всей доски включает все виды карт,
если схема требует отдельный вызов для каждого типа.

## Учитывать границы MCP

- Описания, ответственные и вложения существуют в интерфейсе, но изменять их
  только при наличии соответствующих runtime-операций.
- Управлять участниками и доступами только через явные инструменты с понятным
  эффектом; одной проверки доступа недостаточно для его изменения.
- Не подменять Карту процесса-опыта КРИ или произвольным графом, если MCP не
  предоставляет модель КПО.

## Завершить работу

Сообщить:

- пространство, проект и режим доступа;
- использованные возможности и отсутствующие операции;
- фактически прочитанные, созданные и изменённые сущности;
- фактически созданные пары `strategicBetId ↔ hypothesisId` и неподтверждённые
  межкартовые связи;
- результаты аудита, историю и конфликты версий;
- принятые и отклонённые ИИ-рекомендации;
- созданные файлы экспорта;
- неподтверждённые выводы и следующий безопасный шаг.
