# КПО между стратегией и реализацией

## Вход из Карты гипотез

Получить выбранный контур: цель, гипотезу, её основания, ожидаемое изменение
поведения/процесса, метрики, ограничения, масштаб и горизонт проверки.
Не превращать предположение о механизме в факт текущей деятельности.
Сохранить ID, версии и источник, если они доступны.

Затем определить, какой процесс надо исследовать или изменить.
Цель картирования сформулировать отдельно: например, установить место
потери информации. Она не обязана повторять числовую цель КГ.
Не переносить задачи КГ в точки КПО автоматически.

Если у гипотезы есть признак выделения ресурсов, читать именно этот признак,
а не выбирать по приоритету или предполагаемой отдаче. Финансирование
не подтверждает гипотезу и не означает готовности услуги.
Различать процесс создания услуги, её потребления и оценки результата.
Для КПО изменения поведения начинать с процесса выбранного субъекта.
Разработку, исследования и инвестиционные решения не вставлять в ту же
временную цепочку автоматически: сохранять как условия/источники либо
моделировать отдельно с собственной рамкой по запросу.

Причинная связь гипотезы не является линией следования или взаимодействия.
В проверенном MCP нет специальной связи «гипотеза ↔ узел КПО».
При необходимости сохранить происхождение текстом в поддержанном поле
с явным ID и источником; не объявлять это штатной межкартовой связью.

## Передача в КРИ

Выбрать узлы, для которых требуется проектировать средство или способ работы.
Передать контекст, а не только название:

| Данные КПО | Что уточнить для КРИ |
| --- | --- |
| Участник дорожки | Носитель действия, если он уже определён |
| Условия, соседние точки, события | Ситуация выбора способа |
| Операции | Способ действия без преждевременной формы решения |
| Вход, выход | Объекты и преобразование |
| Барьеры и цель изменения | Зачем нужно действие, ограничения и проверяемый результат |
| Средства и каналы | Существующее оснащение, кандидаты форм реализации; не готовая цель |

Поля не переносить механически один к одному. Одна точка может включать
несколько действий, а некоторые точки вообще не требуют КРИ.
Цель рабочей истории получать из смысла деятельности, не из желаемого экрана.
Перед созданием проверить имеющиеся этапы и истории, чтобы не плодить дубли.

Технически `update_xpm_node_story` связывает один узел с одной историей
через скалярный `storyId`. Прочитать обе стороны в одном проекте,
проверить прежнюю привязку, затем записать и подтвердить её чтением.
Не считать это созданием истории, двусторонней синхронизацией полей
или автоматическим каскадом при удалении.

Если нужно несколько историй для точки, не изобретать `storyIds`.
Сохранить развёрнутое соответствие в отчёте/поддержанном текстовом поле,
а структурную привязку выбрать осознанно. Не дробить точку только ради
ограничения API, если это испортит смысл карты.

## Обратные сигналы

Вернуть в КГ конкретный вопрос, если процесс не способен обеспечить
предполагаемое изменение, отсутствует участник/ресурс или обнаружено
противоречие важной предпосылке.
Указать наблюдение, источник, затронутые ID, ограничение вывода
и предлагаемую проверку. Не объявлять гипотезу опровергнутой по одной
неподтверждённой схеме.

Вернуться из КРИ в КПО, если история меняет последовательность,
взаимодействие, канал, вход или выход. Изменить карту только в пределах
поручения, сохранив различие текущего и целевого процесса.
Техническое решение не является доказательством улучшения опыта.

## Самостоятельное применение

КПО можно использовать без КГ и КРИ, если задача ограничена процессом.
Установка других скиллов не обязательна. При совместной работе передавать
имена соответствующих скиллов и смысловой контекст, не ссылаться
на файлы за пределами папки установленного скилла.
