## Контракт и доступ

Подключение: https://sociotech.center/mcp.
Для точных аргументов прочитать [снимок операций](mcp-operations.md),
затем сверить его с текущим runtime. Имена служат поисковыми ориентирами.

Работать с проектами только через MCP: инструменты, ресурсы и промпты.
Не использовать браузер агента и прямой REST/HTTP API Социотеха.
При `needsAuth`, ошибке подключения или отсутствии операции остановить
зависимую часть. Авторизацию выполняет пользователь в MCP-клиенте;
не просить пароли, токены или коды.

Определить пространство и проект по ссылке/ID или текущему поиску.
При нескольких подходящих проектах получить выбор по различающим признакам.
Проверить `check_board_access` перед записью. Не выводить `canEdit`
из публичности проекта или возможности его прочитать.
Для аудита без записи не вызывать мутации и не применять ИИ-рекомендации.

## Прочитать модель

1. Прочитать обзор проекта и полную КПО через объявленный ресурс либо
   `get_xpm`. Учитывать цель, модальность, позиции мышления и материалы.
2. Сохранить возвращённый ID карты, участников, дорожек, строк, узлов
   и связей. Не конструировать ID и не приравнивать `mapId` к `boardId`.
3. Восстановить принадлежность: карта → дорожка → строка → узел;
   отдельно участники, назначения, связи, слои, вложенные события и `storyId`.
   Фактическую форму JSON получать из ответа, не предполагать её по этой схеме.
4. Для точечной правки дочитать соседние узлы, обе стороны взаимодействия
   и связанные истории, если они меняют смысл.
5. Зафиксировать ревизию через `get_board_revision` и план изменений.

Если чтение не вернуло карту или её идентификатор, не угадывать
`create_xpm_map`. Проверить актуальную модель MCP и сообщить ограничение
инициализации. Наличие пустой КПО и её ID достаточно для заполнения:
не требовать отдельного создания карты, если она уже существует.

## Создать согласованный фрагмент

После получения достаточных оснований и поручения на запись:

1. Записать только согласованные метаданные отдельными операциями.
2. Переиспользовать подходящих существующих участников. Для новых сначала
   создать участника, затем дорожку с его ID; проверить назначение.
3. Создать строки для каналов/ветвей внутри дорожек. Сначала прочитать
   результат создания дорожки: не создавать вторую строку автоматически,
   если нужная строка уже появилась.
4. Создать первую точку в нужной строке. Проверить признак старта
   и при необходимости явно поставить его допустимому первому узлу дорожки.
5. Для продолжения в конце использовать составную операцию либо создание
   отдельного узла и связи. Не добавлять вторую связь поверх автосозданной.
6. Для существующих дорожек создать нужные узлы/связи явно. Для нового
   участника взаимодействия можно использовать `split_xpm_node`,
   затем проверить новую дорожку, строку, назначение и автосвязь.
7. Заполнить слои, условия и подписи связей по подтверждённым данным.
8. Перечитать граф, проверить его и сообщить остаток работы.

Операции ветвления создают топологию, но не решают за аналитика,
являются ветви альтернативами или одновременной работой.
Если автосвязь не соответствует смыслу, изменить её штатной операцией
и повторно проверить.

### Группы взаимодействия

В живом runtime 2026-11-06 подтверждено ограничение: связная группа
`interaction` не может включать две точки одной дорожки. Проверять всю
транзитивную группу: `A1—B1` и `B1—A2` объединяют две точки дорожки A,
хотя каждая отдельная связь соединяет разные дорожки. Сервер возвращал
`Http.400` с сообщением об этом ограничении.

Не менять `interaction` на линию следования ради обхода ошибки.
Сначала проверить смысл: один контакт мог быть чрезмерно раздроблен;
либо следующий контакт действительно требует новой пары точек на тех же
дорожках. Создавать точку только для отдельной ситуации, а не ради API.
Асинхронную передачу и ожидание моделировать по их реальному смыслу.
Если обеспечивающая деталь за выбранной глубиной, сохранить её в аннотациях
и назвать границу, не изображая неподтверждённый контакт.

## Изменить структуру

Сначала сопоставить желаемое изменение с существующими ID.
Переименовывать и перемещать существующий элемент, а не удалять
и создавать его заново ради расположения.

| Намерение | Выбор и проверка |
| --- | --- |
| Добавить продолжение в конце | `create_next_xpm_node`; источник и порядок проверить до/после |
| Вставить точку внутри строки | `create_between_xpm_node` при подходящих соседях и существующей связи следования |
| Добавить предысторию перед первым узлом | `create_previous_xpm_node`; проверить перенос старта |
| Добавить ветвь того же участника | `create_branch_xpm_node`; проверить новую строку и условие |
| Добавить взаимодействующего участника | `split_xpm_node` только если нужна новая дорожка |
| Соединить уже существующие стороны | `create_xpm_link` после проверки отсутствия пары |
| Переместить узел | `move_xpm_node`; `previousNodeId: null` означает начало целевой строки |
| Изменить порядок строк | `move_xpm_row` только внутри текущей дорожки |

Перед вставкой между узлами сохранить тип, подпись и направление прежней связи.
Не предполагать их автоматического наследования: после операции распределить
нужную семантику между новыми связями и проверить результат.
Не использовать `create_between_xpm_node` для узлов разных строк
или вместо связи взаимодействия.

После перемещения проверить обе строки, порядок, старт, аннотации, связи
и `storyId`. Перемещение не считать гарантированным переподключением графа.
Не обещать точные координаты или наклон линий: таких аргументов в снимке нет.

## Обновить слои

`update_xpm_node_layer` принимает один слой, `isEnabled` и массив `values`.
Перед дополнением прочитать весь текущий слой и передать итоговый массив
с сохранением чужих записей; не рассчитывать на автоматическое добавление.
Не смешивать «скрыть слой» и «очистить данные». Эффект отключения проверить
чтением; пустой массив отправлять только для явно требуемой очистки.

`condition` — условия; `input`/`output` — вход и результат;
`channels` — каналы; `operations` — действия; `barriers` — препятствия;
`means` — средства; `custom` — дополнительные сведения.
Не придумывать `duration`, `emotion`, `artifacts` или произвольные ключи
слоёв. При необходимости использовать `custom` с понятной текстовой меткой,
источником и статусом; не затирать прежнее содержимое.

Поддержка зависит от типа узла. В живом runtime 2026-11-06 записи
`input` и `condition` для `trigger` вернули `Http.400` «слой недоступен».
Это наблюдение контракта, а не запрет метода или доказательство недоступности
всех остальных комбинаций. Не перебирать слои мутациями.
Без явного подтверждения поддержки задавать триггер вопросом и подписывать
исходы; подробный критерий можно сохранить в уже поддержанном `custom`
предшествующей ситуации, сохранив прежние значения. Не заявлять это нативным
слоем триггера. Вход/выход обязательной ключевой точки не переносить
механически на триггер или точку вне контроля.

Канал строки и список каналов узла — разные места хранения.
Не распространять изменение одного узла на всю строку без основания.
`precedingEvent`, `accompanyingEvent` и `stage` обновляются как текстовые
вложения с флагом `enabled`. Это не загрузка файла, не самостоятельный
узел `event` и не этап КРИ.

## Связать с КРИ

1. Прочитать узел и его прежний `storyId`.
2. Прочитать существующую историю КРИ и её контекст в том же проекте.
3. Если история ещё нужна, создать её средствами КРИ только в пределах
   поручения; заполнить и проверить до связывания.
4. Передать существующий `storyId` в `update_xpm_node_story`.
5. Перечитать узел и историю, подтвердить точную пару ID.

Операция привязки не создаёт историю и не переносит содержание аннотаций.
Старую связь сохранять, если её замена не входит в запрос.
`storyId: null` снимает привязку; это не разрешение удалить историю.
При нескольких кандидатах не выбирать по одному совпадению названия.

## Проверить результат

Перечитать затронутые элементы и полную КПО. Сопоставить с планом:

- нужные участники, дорожки, строки и узлы существуют ровно по назначению;
- исходные ID и незатронутые данные сохранены;
- порядок и старт согласованы;
- все связи имеют существующие концы и правильный смысл, без дублей;
- подписи, типы, направление, флаги и значения слоёв сохранены;
- рабочие истории существуют и соответствуют ожидаемым `storyId`;
- фактические изменения отражены ревизией/историей при их доступности.

Запустить `audit_xpm`. Его заявленный охват — начальная ключевая точка,
обязательные вход/выход и нарушенные ссылки. Не приписывать ему проверку
всей нотации, причинности, качества опыта или полноты процесса.
Требование сервиса к заполнению не даёт оснований выдумывать данные.
Для незавершённого исследования вернуть замечания и причины.

## Частичный сбой и конкурентность

При тайм-ауте или ошибке прекратить зависимые операции и перечитать состояние.
Ответ с ошибкой не доказывает отсутствие эффекта. Найти фактически созданные
элементы, записать их ID и только затем решать, что продолжить.
Не повторять составную операцию вслепую: она могла создать несколько объектов.

Проверять и MCP-флаг `isError`, и возвращённый JSON `success: false`.
Не считать вызов успешным только по факту ответа инструмента.
После подтверждённой ошибки допустимости адаптировать пакет к контракту,
сохраняя смысл; не обходить ограничение заменой нотации.

При смене ревизии перечитать затронутые поля и пересчитать пакет.
Не передавать выдуманный `expectedVersion`: XPM-схемы снимка его не принимают.
Без серверного условия версии нельзя обещать атомарность; работать малыми
сериями и сообщать неразрешённые конфликты.

## Удаление и неподдержанные операции

Удалять только в пределах явного поручения. Перед удалением строки/дорожки
показать состав и затрагиваемые связи; выяснить каскад по текущему описанию.
Удаление узла явно удаляет его связи. Не предполагать аналогичные каскады
для всех остальных сущностей и не обещать Undo.

Отсутствующие операции назвать по смыслу. Не считать строковый `mapType`
разрешением экспортировать XPM; текущий экспорт перечисляет другие карты.
Если нужен ручной шаг, его выполняет пользователь; агент не обходит MCP.
